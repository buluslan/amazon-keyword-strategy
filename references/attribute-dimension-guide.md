# 属性维度构建指南

> 触发时机：Step 3 打法分析，归纳属性维度前读（`word_root-classification.md` 属性词根节的两层打标用到）。
> 定位：教你**从本次词库现场构建维度**的流程与验收标准。这不是分类库——没有任何预设维度清单可以直接取用。

---

## 一、构建流程（从数据长出维度）

对本次词库按序执行：

1. **修饰类 token 频次统计**：把词库全部词打散成 token，统计频次，找出高频修饰类 token（剥掉共性词后剩下的成分）
2. **按语义相近聚簇**：语义指向同一决策角度的 token 归为一簇（含拼写变体、同义变体）
3. **对每簇问一个问题：「买家是按这个在挑产品吗？」**
   - 是 → 命名成维度，进入下一步
   - 否（纯装饰词、无决策含义）→ 不建维度
   - 指向品牌归属 → 不建维度，走品牌双分类（`word-root-classification.md`）
   - 指向"本品不具备的规格" → 不建维度，走规格锚点否定判定
4. **每维填 tags**：簇内 token 及其变体即该维取值
5. **用四条标准自查，删不合格维度**（见第三节）

## 二、输出契约（维度的骨架格式）

每个维度四个槽位：

| 槽位 | 内容 | 例（格式示意，非内容预设） |
|---|---|---|
| 维度名 | 一个买家决策角度的命名 | `<维度>` |
| purpose | 买家在按什么挑，一句话 | 「买家按 `<角度>` 挑产品」 |
| tags | 该维取值（簇内 token + 变体） | `<tag1> / <tag2> / …` |
| 衔接说明 | 该维进哪个体系出口 | 属性打标 / 规格锚点来源 / 兼容生态处理 |

产物落 `root_dims`（token → 维度名映射），随 payload 注入——render 聚合进词根汇总的「属性维度」列与属性机会 Top。

## 三、好维度四条标准（自查硬门槛）

1. **正交**——维度间不重叠，一个 tag 只归一维。两个维度语义有包含/交叠关系 = 合并或重划
2. **长自数据（机械化验证）**——每个维度必须能指认词库中支撑它的具体 token 簇（列出这些 token）。指不出簇的维度 = 删
3. **可判别**——每维 tags 能区分词库里的真实词。一个 tag 都命中不了词库词的维度 = 空维度 = 删
4. **落得进打法**——维度至少服务四个出口之一：属性打标（`属性·<维度>`）/ 规格锚点 / 否定判定 / 属性机会聚合（词根汇总机会分）。哪个出口都不服务的维度 = 删

**常见坏维度特征**（对照自查）：
- 粒度忽粗忽细——一个维度是具体接口级，另一个是大类功能级，混杂无层级规则
- 品牌词混当属性维——品牌归属是品牌双分类的事，不是属性维度
- 维度互含——两个维度名不同但语义重叠，词没法唯一归维
- 为凑数硬造空维度——数据里没有支撑簇，为了"看起来全"而造

## 四、提问角度启发（非清单，仅供参考）

归纳维度卡住时，可以从"买家挑这类产品时在问什么"的角度观察词库：它长什么样、什么形态？解决什么问题？谁在用、在哪用？什么规格参数？要跟什么搭配使用？图什么价值主张？什么季节或节点会用？

**这是提问角度的启发，不是分类库**——上面的问句不构成默认维度集。维度由本次词库的数据决定，不由这份提示决定。

## 双向硬规则

- 提示里有的角度，本次数据不支撑 → **不建**
- 提示里没有的角度，本次数据支撑 → **照建**
- 维度数量无预设（3 维合法，9 维也合法），唯一裁判是数据
